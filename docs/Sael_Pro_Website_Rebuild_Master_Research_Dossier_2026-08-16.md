# 4. Creative process — synthesis from Saël's previous website and recent conversations

This section is especially important. The new website should not have a conventional “process” page made of corporate design-thinking diagrams.

Saël already has a distinctive way of thinking.

## 4.1 Start from the intended condition, not the medium

Saël's software-development dossier says his systems-oriented approach generally begins with the **interaction or operational problem**, then determines what combination of applications, services and infrastructure is appropriate.

The same logic appears in his creative work.

He does not naturally begin with:

> “I want to use TouchDesigner.”

or:

> “This should be VR.”

The stronger starting question is:

> **What should a person experience, notice, understand, remember, or do?**

Only then does the medium become a design decision.

This is a key distinction for the website.

## 4.2 Constraints are not obstacles; they are generative material

The existing sael.pro text describes a mindset of receiving and digesting many ideas and taking constraints as motivations.

This remains characteristic of Saël's current work.

Practical constraints are brought into the creative process early:

- venue;
- hardware;
- field conditions;
- budget;
- audience;
- operator;
- travel;
- bandwidth;
- safety;
- environmental conditions;
- installation time;
- distribution.

The goal is not to “protect the concept” from reality. The goal is to discover the version of the concept that becomes **stronger because it understands reality**.

## 4.3 Define “golden rules”

The current website describes defining a set of targets ranging from emotional effects to physical perspective, then using them as “golden rules.”

This should survive the redesign, though in cleaner language.

A useful reconstructed process:

1. define what must remain true;
2. identify what the audience should perceive or feel;
3. understand the physical and operational environment;
4. establish the rules that cannot be compromised;
5. design every subsystem against those rules.

This explains why Saël moves naturally between artistic and technical decisions: both are evaluated against the same experiential objective.

## 4.4 Experience first; explanation second

Recent development of Azul Vivo sharpened this into a clear artistic principle:

> **experience first, explanation second**

The audience should be allowed to encounter something before the system explains it.

This has consequences:

- no unnecessary labels over an underwater animal;
- no interaction simply to prove a system is interactive;
- no dashboard when one gesture will do;
- no “technology showcase” that competes with the experience.

This is a broader philosophy, not only an Azul Vivo rule.

## 4.5 Technology should disappear when it has done its job

This idea appears repeatedly across Saël's work.

The previous site says technology should be integrated seamlessly with the physical environment and communicate bilaterally with it.

Recent work goes further: the system can be extremely sophisticated while the user's encounter remains simple.

Examples:

- a PWA can know timecode, shot metadata, species, location and semantic events while the user sees one button: **Remember this moment**;
- a touring installation can have complex networking, playback and orchestration while the visitor sees only a responsive environment;
- physiological sensing may involve firmware, cloud routing and multi-user synchronization while the artistic question remains about presence and perception.

The new website should **show technical depth without fetishizing the stack**.

## 4.6 Interaction is not the same as input

Saël is skeptical of interaction used as spectacle.

Especially in immersive work, he resists the pattern:

> participant moves → particles move

unless that interaction actually contributes to meaning.

A more characteristic interaction is:

- observe;
- discover;
- remember;
- affect a shared system indirectly;
- reveal a hidden relationship;
- let physical context alter digital behavior;
- let the system become attentive to the participant.

This can become an important statement on the website.

## 4.7 Build the whole relationship, not isolated components

OnMove is a strong example.

The interesting accomplishment is not simply “React frontend” or “Flutter app.” It is the architecture connecting:

**authoring → backend → content → identity → location → mobile/browser playback → physical place**

Echoes does the same:

**body → sensor → firmware → protocol → mobile app → network → cloud → desktop → realtime media**

Saël's work is often strongest when represented as **chains, systems, flows, or ecosystems** rather than isolated deliverables.

## 4.8 The visitor is not the only user

The current sael.pro text makes an unusually useful point: experience design includes everyone around the project.

That means:

- visitor;
- curator;
- technician;
- operator;
- stage manager;
- producer;
- maintenance team;
- sponsor/client where applicable.

A great public-facing experience that is miserable to install, diagnose, tour, reset, or maintain is not a fully designed experience.

This is especially relevant to Saël's current systems-architecture practice.

## 4.9 Prototyping is a way of thinking

Saël repeatedly builds partial systems in order to discover what the final system needs to be.

This includes:

- software prototypes;
- 3D-printed parts;
- small physical rigs;
- projection tests;
- realtime media tests;
- underwater camera/ballast systems;
- fulldome tests;
- temporary application experiments.

The site should make room for **experiments**, not only polished “case studies.”

## 4.10 Precision without rigidity

There is a productive tension in the practice:

- engineering requires precision;
- artistic work requires discovery;
- field work requires adaptation.

Saël's strongest process does not eliminate uncertainty. It creates a structure robust enough to work with uncertainty.

Echoes provides a useful conceptual example: human physiological signals are noisy and probabilistic, unlike a deterministic cue system. The system has to preserve uncertainty rather than pretending the data is absolute.

The same mindset appears elsewhere: systems should be exact about what can be known and flexible about what cannot.

# 5. Personality / working style the site should convey

This is not a personality diagnosis. It is a practical synthesis of how Saël approaches projects and decisions.

## Curious across domains

The practice is unusually broad because Saël tends to follow a question across disciplinary boundaries rather than stop where a job title stops.

If understanding the problem requires:

- code;
- optics;
- 3D printing;
- networking;
- interaction design;
- underwater filming;
- cloud architecture;
- fabrication;
- biology;
- projection geometry;

he tends to learn enough of the adjacent discipline to make informed design decisions and collaborate effectively.

## Systems-minded

Saël tends to think in dependencies, interfaces, constraints, failure modes, and flows.

Even creative ideas are often turned into structures:

- timeline;
- data model;
- interaction grammar;
- signal path;
- scene logic;
- decision register;
- technical topology.

## Independent but collaborative

He is comfortable carrying a project across many disciplines himself, but the strongest description is not “one-man army.”

A better formulation is:

> able to hold the whole system in his head, build substantial parts directly, and collaborate with specialists without losing the coherence of the experience.

## Iterative

Ideas are tested, challenged, reframed and rebuilt.

The site should avoid presenting the process as a linear march from “idea → design → build.” The actual method is closer to loops:

**observe → frame → prototype → test → learn → restructure**

## Anti-gimmick

Saël tends to reject technology whose primary justification is novelty.

The right question is not “is it cool?” but:

- does it belong?
- what does it reveal?
- what does it make possible?
- does it increase presence or fragment attention?
- does the audience understand what to do without being instructed through the interface?

## Detail-sensitive, operationally aware

The current website explicitly values finesse, team relations and scheduling alongside aesthetic decisions.

This has become more important, not less, as projects grew in scale.

# ECHOES
**Years:** 2023–2024 principal development period  
**Role:** Creator / System Architect  
**Type:** Biometric middleware + realtime physiological data platform  
**Context:** Kommon.io; technology later transferred to Supply + Demand

## Concept

Echoes explored how physiological and neural signals could move through a complete technical pipeline and become usable by realtime multimedia environments.

## System chain

**human body → sensing hardware → firmware → device communication → mobile app → realtime/cloud transport → user/session aggregation → Windows client → external media environment**

## Technologies / research
- EmotiBit physiological sensing;
- Emotiv MN8 EEG;
- modified EmotiBit firmware;
- Bluetooth;
- USB serial;
- Wi-Fi;
- Flutter mobile app;
- Flutter Windows client;
- Firebase;
- realtime multi-participant data;
- session/user association;
- authorization;
- encrypted/anonymized transport;
- temporal synchronization.

Project records attribute approximately **2,101 development hours in 2023–2024**.

## Conceptual importance

Echoes changed Saël's relationship to interactive media.

A conventional interactive installation asks:

> How can the participant affect the media?

Echoes asks at a deeper level:

> What signals are actually coming from the participant, and how do we preserve their temporal and embodied meaning?

This later becomes an inversion in Azul Vivo research:

> **Echoes: how can the body influence an immersive system?**  
> **Azul Vivo: how does an immersive system influence the body?**

## IP note

Specific transferred Echoes code/IP should not be presented as current independent Saël IP without checking rights.

Saël's acquired expertise is part of his professional practice; the transferred software assets are a separate question.

- HUD overlays;

## A more fitting visual metaphor

Think of **systems revealed only when useful**.

For example:
- a project card starts as image + one sentence;
- hover/tap reveals role and system layer;
- a case study can toggle between **Experience** and **System** views;

- a technical layer can sit beneath an emotional/visual layer.

**complexity underneath, clarity at the interface**.

Use strong, neutral typography with unusually good spacing and hierarchy rather than “tech fonts.”

## Motion

Motion should communicate:
- relationship;
- transformation;
- revealing layers;
- flows between components.

Do not animate everything.
